- 1.1 老项目改造的“恒定本质”：理解 + 开发

 ▫ 改造老项目永远绕不开两件事：

 ⁃ 理解项目：架构、依赖、约束、历史包袱。

 ⁃ 理解本次需求：业务目标、边界、影响范围。

 ⁃ 然后才是开发：写代码、补测试、改文档。

 ▫ AI Coding 只是改变了“工序的分工”，没有改变“理解 → 决策 → 开发”的主线。

 ▫ 这门课的核心贡献：不是发明新方法论，而是把每一步“人干什么、AI 干什么、怎么验收”流程化、标准化，让每次都尽量稳在“80 分以上”的质量，而不是心情好才 90，心情差直接翻车。

- 1.2 “AI 是加速，不是兜底”的方法论落点

 ▫ AI 可以极大压缩的是体力活：

 ⁃ 写需求文档、扫代码找影响面、画链路图、列改造点、写样板代码、生成测试、同步文档。

 ▫ AI 无法兜底的是关键判断：

 ⁃ 业务方向对不对、哪些边界要产品拍板、哪些不在本次范围内、现状到底长什么样、哪些决策是“有风险的 D2 / D3 决策”、测试断言依据事实而不是“应该如此”、最终代码 review。

 ▫ 这节课所有后续四问，都是在拆解这句话：哪里是“加速”，哪里是“不能兜底”。

工具每年都在换风口，但老项目改造的工作流长期稳定：

 ▪ 理解项目：看代码 + 看文档 + 问业务。

 ▪ 拆需求：六维 + 边界 + 决策。

 ▪ 拆方案：链路 + 改造点 + 影响分析。

 ▪ 改代码：小步提交 + 测试 + review。

 ▪ 沉淀：更新资产 + 经验写进 CLAUDE.md。
