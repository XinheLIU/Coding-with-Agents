# 规格编码：把想法交付成产品的六步流程

Last updated: 2026-11-10

> 本章为草稿：六步交付流程已可阅读；六维需求体系与规格→验证的交付闭环仍在撰写中。

**规格编码（Spec coding）**是规格优先的开发方式：先把要做的东西写成智能体可以直接执行的规格，再让智能体在约束和验证下完成实现。与之相对的**氛围编码（Vibe coding）**适合探索；当你要交付一个真正的产品时，规格编码是把「想法」变成「可验证变更」的工程路径。

本章给出一套可直接套用的六步流程。它本质上是 [Harness Engineering](../02-anatomy/README.md) 思路在个人或小团队项目上的落地：前四步都在为智能体搭建施工环境，真正的编码从第五步才开始。

---

## 第一步：写完整的 Spec 文档

把 Idea 草稿和 Demo 交给 AI，用简单提示词让它细化所有需求功能，完成详细的 PRD 文档。

这一步的产出决定后面所有步骤的质量。规格里所有含糊的地方，都会在智能体构建出的东西里现形——所以宁可在这一步多迭代几轮。

## 第二步：定 UI/UX 设计标准

参考 Dribbble、RecentDesign、Mobbin 等设计网站，让 AI 从参考图中提炼：

- 配色体系
- 按钮 / 圆角风格
- 卡片、图表、状态反馈的样式
- 文案规则

产出一份 `DESIGN_STANDARDS.md`。后续每次改界面都按同一套标准执行，避免越改越乱。这份文件如今已有通用格式 DESIGN.md，写法与配套的设计 Skill、浏览器验证闭环见[智能体前端开发](agentic-frontend.md)。

## 第三步：做开发架构设计

根据 PRD 让 AI 生成具体的技术调研方案。架构文档相当于给 AI 画施工图——没有它，每个任务都会各自为政地选型。为什么要把产品、业务和工程底座分开设计，以及工程组件如何初始化、如何在演进中提炼，见[产品、业务与工程底座](product-business-engineering.md)。

## 第四步：建立项目管理与长期记忆

延续 Harness Engineering 思路，让 AI 建立可回溯的长期记忆。生成的文件要分成两组，因为它们的寿命完全不同：

**长期记忆**——跨任务保留，只存智能体从代码里读不出来的东西：

| 文件 | 作用 |
| --- | --- |
| `AGENTS.md` | 告诉后续 AI 项目是什么、目录怎么读、从哪里开始，以及关键决策背后的原因 |
| `docs/decisions/` | 记录技术决策及其理由（Why），而不是复述实现细节 |

**工作状态**——服务于当前这一轮交付，有明确的生命周期：

| 文件 | 作用 | 生命周期 |
| --- | --- | --- |
| `tasks.json` | 拆解出可执行的任务列表 | 任务全部完成后归档 |
| `progress.md` | 每次完成后记录进度 | 本轮交付结束后归档或清空 |
| `init.sh` | 新 session 时快速恢复项目上下文 | 随工作状态一起更新或删除 |

本质是让 AI 在长期任务中始终可回溯进度——任何一次新会话都能从文件系统里重建「项目现在在哪」。但不要把工作状态混进长期记忆：过期的进度会让下一次会话「恢复」出一个已经不存在的现场。两者的划分原则见[代码库记忆](repo-memory.md)。

## 第五步：真正开始 coding

按 `tasks.json` 一个任务一个任务做。每完成一个任务先验收，确认没问题再进入下一步——以浏览器插件为例，验收就是三个问题：能否构建成功？能否在 Chrome 加载？side panel 能否打开？

核心原则：**让智能体像人类工程师一样在迭代、反馈中逐步完成，而不是一次性生成。**

## 第六步：版本管理

第一个 coding 任务完成后，提交到 Git 仓库。之后每次完成任务，确认 `progress.md` 已记录进展。

每次提交前再做一次**蒸馏**，问两个问题：

- 这次实现中有没有做出新的取舍、踩到新的坑？有就把**原因**写回 `docs/decisions/` 或 `AGENTS.md`。
- 有没有哪部分 Spec 已经被代码和测试完整实现？有就把它标记为已实现并归档，不再让它充当智能体的参考。

反复迭代第五、六步，直到产品完成。

---

## Spec 的生命周期：从施工图到 Why

六步流程里的 Spec 写得非常细：需求、设计标准、架构、任务拆解，几乎全是 What 和 How。这在**实现之前**是对的——那时代码还不存在，Spec 是这些信息唯一的家。

问题出在实现之后。另一派实践者对规格驱动开发有尖锐的批评：Matt Pocock 长期尝试「specs-to-code」后发现代码质量逐轮下降，认为「The code is the battleground, not the spec」；poteto（Lauren Tan）则说「the best spec is code」。他们共同的担忧是 **doc rot**：代码已经变了，Spec 还停在原地，继续误导后续的智能体。

两种立场的分歧其实是时间上的。一旦实现落地，Spec 中的 What 已经由代码承载，How 已经由测试、lint 和 Skill 承载，再保留一份就是同一个事实维护两遍。正确的做法是让 Spec 走完它的生命周期：

```text
Spec（施工图，临时）
   │  实现
   ▼
代码 + 测试 + 工具（What 与 How 的新家）
   │  蒸馏
   ▼
决策理由（Why，长期留在代码库记忆中）
```

这样，Spec 在实现前提供足够细的引导，在实现后让位给代码，只把代码表达不了的那部分——为什么这样设计、放弃了哪些方案、在什么前提下要重新考虑——沉淀为长期记忆。详见[代码库记忆：只存 Why](repo-memory.md)。

---

## 小结

六步流程的前四步（Spec、设计标准、架构、项目管理）都不写产品代码，它们回答的是同一个问题：**如何让智能体在长期任务中不迷路**。规格是施工图，设计标准和架构文档是施工规范，`tasks.json` 和 `progress.md` 是施工日志。第五、六步在这套约束里小步迭代——每个任务先验收再前进，每次进展落盘可回溯。这正是规格编码与一次性生成的区别：交付的不是一段代码，而是一个可验证、可续接的工程过程。
